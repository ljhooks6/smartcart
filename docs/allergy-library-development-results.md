## Implemented

- **48 authored engineering candidates: 36 dinners / 12 desserts**, 33 dinner families. Metadata includes ID, revision, family, required equipment and engineering-candidate status. Three new generic identity records bring the catalog to 59 profiles. No practical cooking or professional review is implied. Related variants share a family rather than falsely counting as unrelated meals.
- Deterministic per-job selection uses the last three owner-matched completed plans within 14 days, current rejected recipes and recent owner-matched rejected inputs. Ranks entire families, not only exact titles. Hard scope, ingredient, budget, pantry, equipment and estimated time checks run first; conservative batch-time allowances prevent a large household from inheriting a small-pan timing claim. Constrained repeats are disclosed. An optimistic cost bound rejects impossible plans without relaxing checks or making AI calls.
- Local authenticated adapter: `POST /api/labs/allergy-library`. Uses verified local Supabase identity, explicit synthetic UUID allowlist, existing server product-access/agreement eligibility and effective Free/Plus RPC. Both current and original restrictions are checked. **Only explicit Milk/Eggs/Peanuts/Sesame combinations** are accepted; unsupported additional sources, custom, medical, intolerance and unclear legacy entries remain blocked.
- Existing job reserve/claim/lease/fencing/finish RPCs are reused. The approved counting policy is implemented: one successful seven-dinner library plan consumes one existing weekly plan allowance (Free 5 / Plus 20). Failed jobs release reservations; same-key retries, saved reads, recipe replacement and groceries do not reserve another plan. Stored input includes mode, catalog version and restrictions in its existing hash. There is no provider fallback or Vercel queue dispatch from this local adapter.
- HMAC-SHA-256 provenance uses **local ephemeral test keys only**. Capsules bind owner, audience, artifact/job, portions, full input/original exclusions, exact recipe revisions/digests and catalog/component digest. Strict signature parsing, constant-time comparison, owner checks and current content validation run on every checked operation. Rotation accepts an old key only while explicitly configured; removal revokes its artifacts. Signed metadata proves integrity, not actual food safety, professional review or authorization.
- Vault/week saves use an **authenticated client**, existing RLS/cap triggers and the atomic weekly-save RPC, not privileged writes. Vault IDs make a repeated artifact save idempotent. No pantry memory is changed (`pantry: null`). Canonical recipes are rebuilt when reopening, so edited names/ingredients/steps do not become authoritative. Historical/stale/tampered content stays stored and returns an unchecked/error state. Grocery transformations reject added, omitted, unknown, conflicting, unit-swapped or changed-quantity food. Replacement uses only fixed authored IDs and preserves current + signed original restrictions.
- Local mobile-responsive account exercise provides password sign-in for disposable accounts, new-plan vs same-request retry, fixed steps, Vault/week saves, reopening and canonical grocery requirements. Tokens stay in memory; no account plan or service credential is displayed. The ordinary production application is not switched to this mode.

## Local configuration / isolation

Both `MEALCADDIE_ALLERGY_LAB=true` and `MEALCADDIE_ALLERGY_INTEGRATION=true` are required, alongside `NODE_ENV=development`, no `VERCEL_ENV` and no `VERCEL`. API requests must be loopback and same-origin for writes. Hosted access is denied before auth, parsing or database access, even if flags are mistakenly set.

Local-only configuration names (no values committed):

- `MEALCADDIE_ALLERGY_LOCAL_SUPABASE_URL`: HTTP loopback disposable API only.
- `MEALCADDIE_ALLERGY_LOCAL_ANON_KEY` and `MEALCADDIE_ALLERGY_LOCAL_SERVICE_KEY`: distinct local lab credentials. Configuration classification prevents returning a service-role key as the public key; user authorization still uses server verification.
- `MEALCADDIE_ALLERGY_LOCAL_SIGNING_KEY`: random base64url key of at least 32 bytes. No production signing key was created.
- `MEALCADDIE_ALLERGY_LOCAL_USER_IDS`: explicit disposable UUID allowlist.

These clients are separate from the existing cached shared-project client and never fall back to its URL or credentials. No shared migration is required or applied. JSON data remains in the existing saved-content tables; existing content and retention behavior are preserved. Capsules contain private restriction data and are not encrypted: keep them in owned storage, not URLs, logs, public reports or telemetry.

Reproduce pure evaluation: `node scripts/prepare-allergy-review.mjs`. Run automated suite: `node --experimental-strip-types --test --test-concurrency=2 tests/*.test.mjs`. The opt-in `scripts/test-allergy-library-local.mjs` requires `RUN_DISPOSABLE_ALLERGY_LAB=1`, the unlinked loopback Auth lab, Docker and the already-installed local `pg` module path in `MEALCADDIE_LOCAL_PG_MODULE`. It creates two synthetic `example.invalid` identities (confirmed administratively **only in the local test lab**, no mail), a new disposable database and a cached PostgREST container bound to loopback, then removes only those resources. It never pulls an image or changes existing service settings. The adapter is invoked with real local Auth sessions and REST clients.

## Genuine remaining blockers before a hosted pilot

1. **Qualified review and practical cooking:** all 48 revisions remain NOT REVIEWED / NOT TESTED. See the [review packet and unsent shortlist](allergy-review-packet/README.md). Flatbread/gnocchi/dumplings, eggless binding, cocoa-square texture, batch times and yields need particular attention. Reviewer may reject candidates or narrow scope; no claimed numerical target overrides that finding.
2. **Security/release review:** inspect signing implementation, canonicalization, key rotation/revocation, request limits and owned-storage/cache behavior before hosted activation. No new production keys or hosted allowlist are approved or provisioned. Ordinary application-wide navigation/rehydration/Cook/Shop wiring remains deliberately disabled; the functioning integration is the isolated local adapter/exercise. A future app-wide adapter must preserve signatures and never turn dropped metadata or cached ordinary recipes into checked status.
3. **Pilot configuration, privacy and accessibility:** review the exact approved recipe manifest, minimum stored restriction data, consent, stop/expiry procedure, physical device and full NVDA/VoiceOver/TalkBack results. Then separately approve named participants, hosted configuration and protected-preview activation. Existing beta enrollment is not permission for this source-exclusion pilot.
4. **Retail reality:** prices are illustrative use-costs, not package/basket quotes; generic names do not establish any actual product's composition or cross-contact status. Packaged-product evidence (IMP-003) is deferred. Unknown products stay unavailable.

Approval to contact a selected reviewer is still needed before outreach, followed separately by scope/budget approval. The deterministic quota policy is **already approved and implemented locally**; it does not need another product decision. Production deployment and lifting the public allergy restriction remain separate future release approvals. Disable the new mode/allowlist and retire affected signing keys/revisions for pilot rollback; preserve content and existing entitlements. No automatic user-data deletion is introduced.
