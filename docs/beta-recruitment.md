# Beta recruitment — Phase 1

## Release boundary

Work is isolated on feature/beta-recruitment. Do not merge into main, promote a deployment, publicly launch recruitment, or send beta emails without explicit owner approval. This overrides the general automatic deployment preference in development-workflow.md for this program. Preview deployments must retain Vercel Authentication. Do not generate an anonymous share/bypass URL for recruitment review.

The existing MealCaddie app, accounts, guest access, Formspree Plus waitlist, account plan/beta_status, Stripe records and webhooks stay separate. The scoped checkout fix verifies a Supabase identity and derives email/plan on the server. Stripe is mocked in regression tests; checkout is not enabled in the interface.

## Routes and data flow

- /beta: application, using the existing logo, design tokens and mobile layout. Exact recruitment targets are private.
- /beta/privacy: beta-specific privacy notice, provisional pending legal review.
- /admin/beta: an unauthenticated shell contains no applicant data. Existing Supabase login is reused; every directory operation verifies the token and the live admin allowlist. Search travels in POST bodies, not email-bearing URLs.
- /api/beta/applications: bounded JSON, strict validation, network rate limiter, honeypot, server-validated Turnstile, then service-role-only submission RPC.
- /api/beta/admin: private no-store responses, verified administration, transactional review/cohort changes and audit history.
- /api/cron/beta-retention: separate CRON_SECRET authorization, service-role-only retention cleanup.

All seven beta tables have RLS enabled, explicit restrictive browser-denial policies, and direct privileges revoked from PUBLIC, anon and authenticated. Even admins use server endpoints. Functions use SECURITY INVOKER, empty search_path and explicit service_role execution grants. No service key is exposed to client code. Admin authorization is based on an exact confirmed auth.users UUID, never matching email or user_metadata. Admin revocation is checked per request and again during mutations.

Initial administration is seeded separately after the owner confirms the exact user UUID, verifying that UUID still exists in auth.users and has the expected confirmed identity. ## Selection and invitation workflow

Applications store plan interest (Free, Plus, either), frequency, challenges, bounded interests, feedback willingness, source/campaign and separately timestamped beta/marketing consent. Uniqueness is per program and lowercased/trimmed email. Duplicates return a generic response and never overwrite review decisions or consent. Source and campaign are unverified attribution, not identity; no arbitrary referrer URLs are stored.

Status starts Applied. Move to Under Review, then Approved, Waitlisted or Declined. A closed decision can return to Under Review, except Withdrawn cannot be reinstated. Withdrawal revokes marketing consent, releases the cohort seat and deletes invitation drafts. Reserve is assigned to waiting/review candidates; approval requires Free or Plus. All non-declined/non-withdrawn cohort assignments reserve a seat. Program-row locks serialize assignments and target edits; targets cannot be lowered below occupied seats. Counters show assigned cohorts, each status and application sources independently. Recruitment can accept more applications than available seats.

Invited and Activated exist in the schema and dashboard, but Phase 1 transitions into them are disabled. An approved Free/Plus applicant can have an invitation draft prepared. There is no delivery worker/provider, token redemption endpoint, account creation or entitlement grant. Every changed review invalidates an old draft. Later phases must add versioned branded templates, recipient-bound single-use hashed tokens, delivery receipts/idempotency, expiry and verified redemption, and an independent server-side beta entitlement design. Paid/account entitlements must take precedence; never simulate beta access by editing a client value or a Stripe subscription.

## Configuration and setup checklist

Existing Supabase public URL/anon key and server-only service role key are reused. Set credentials directly in the platform dashboard; do not paste them in chat or commit them.

- NEXT_PUBLIC_TURNSTILE_SITE_KEY: configured widget with exact approved preview/production hostnames.
- TURNSTILE_SECRET_KEY: server-only widget secret. Validation checks success, hostname and action beta_application; failures/outages do not store an application. Test keys belong only to an isolated test setup, not production.
- BETA_RATE_LIMIT_SECRET: independently generated server-only random value (at least 32 characters), separate from service-role keys. Only HMAC network identifiers are retained. Vercel's overwritten x-vercel-forwarded-for header is used; submitted IPs/cookies cannot select a different bucket.
- CRON_SECRET: independently generated server-only random value (at least 32 characters). Required for retention scheduling after an approved production deployment. For an authorization-only check, request /api/cron/beta-retention?dryRun=1 with the exact Bearer CRON_SECRET header. A valid check returns authorized:true and cleanupPerformed:false without opening a database client or deleting anything. Missing/invalid credentials return 401; invalid dryRun values return 400 after authorization. Never call the route without dryRun=1 during a controlled preview test: that runs cleanup.
- BETA_APPLICATIONS_ENABLED: defaults off. Leave false for the initial protected review preview.
- BETA_PUBLIC_LAUNCH_APPROVED: defaults off. Required only for production beta routes.
- BETA_PRIVACY_REVIEW_APPROVED and BETA_CONTACT_MAILBOXES_VERIFIED: default off. Both required for production beta routes, alongside launch approval and application enablement.

Do not change production variables or add domains for this preview. Preview rendering can work while submission is disabled. Once Turnstile is configured, explicitly enable preview-only submissions for an authorized functional test; do not enable public production applications.

Verify support@mealcaddie.app receives privacy requests and beta@mealcaddie.app is ready for branded beta messages. SPF/DKIM/DMARC and delivery-provider decisions belong to the branded-email phase. No new email service subscription is required by Phase 1.

## Privacy, consent and withdrawal operations

The owner provisionally approved the notice/retention choices. Obtain appropriate legal review for the actual participant jurisdictions and age policy before setting BETA_PRIVACY_REVIEW_APPROVED. Verify provider disclosures, consent wording, international processing and backup handling; this implementation is not a completed legal review.

General marketing consent is optional, separate and does not influence selection. Recording it does not subscribe applicants to Formspree or authorize this implementation to send campaigns. The admin can revoke marketing consent independently. No application answers go to AI models. Do not log emails, tokens, application answers or raw network addresses.

For a withdrawal request received at support, verify the requester through an authenticated account or other appropriate ownership verification without disclosing another person's application. Mark the record Withdrawn; do not change their MealCaddie account or subscription. Application histories and invitation drafts cascade on deletion. Support staff must confirm completion and keep only minimal verification/deletion evidence under an approved policy. On backup restoration, suspend recruitment and reconcile deletion requests before resuming; backup expiry and support-inbox retention need legal/operational review.

Retention deletes unselected records 90 days after recruitment closure; approved/invited/activated records 90 days after beta end; withdrawn records are eligible at day five, providing daily-job headroom for deletion within seven days. Network counters expire after 48 hours and are removed at the next daily sweep. Program audit events contain no application answers and expire after 180 days. Keep zero-PII cleanup counts for monitoring. Daily scheduling is configured at 08:00 UTC; it activates only upon production deployment, not previews. Configure the secret and monitoring, and test cleanup before launch. If the schedule fails, run admin cleanup immediately and resolve the failure before intake resumes.

## Verification and review

Run npm run test:beta, npm test and npm run build under Node 22. Security tests cover role denials, spoofed identities, revoked administrators, strict inputs, Turnstile failures, duplicates, stale decisions, locked cohort capacity, private draft preparation, consent withdrawal and cascading retention deletion. Existing meal, recipe, generation and membership regressions remain in the full suite. Checkout tests mock Stripe and assert unchanged price, subscription mode, customer reuse, metadata ownership and redirects.

The dashboard currently uses manual verified support handling for withdrawal; there is no unauthenticated withdrawal endpoint or email-based privilege grant. Actual admin-browser testing requires signing in as the confirmed account on the preview origin. A production-origin login does not automatically sign you in to a separate preview domain. Confirm allowed OAuth redirect URLs in Supabase for the exact protected preview before using Google there; do not broaden redirects unnecessarily.
