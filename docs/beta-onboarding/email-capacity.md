# Email capacity recommendation — no rate change

Read-only Resend dashboard review on 2026-10-11: transactional Free plan, 2/100 daily and 2/3,000 monthly, account API limit 10 requests/second. SMTP and invitation API traffic share the account allowance. Shared Supabase authentication remains at the previously verified 2/hour; this work makes no auth configuration change.

Recommend considering 30 authentication emails/hour for the controlled beta, **only after separate approval**. Keep per-user resend protection, OTP lifetime/settings and exact redirects unchanged. The custom SMTP project-wide allowance is configurable; it is not a provider quota increase. See [Supabase rate limits](https://supabase.com/docs/guides/auth/rate-limits) and [Resend usage limits](https://resend.com/docs/api-reference/rate-limit). Dashboard account limits take precedence over generic defaults.

Model, not measured production traffic: one 15-person daily wave, one invitation each plus up to two auth emails each = 45 emails/day. A 20-message existing-traffic reserve gives 65/day, below 100. Three such waves on separate days need 135 messages total. Sending all 45 candidates the same day under that assumption needs 135 and exceeds the daily allowance. At 2 auth/hour, 30 auth messages need at least 15 hours of quota capacity; 30/hour better accommodates a wave but does not permit unlimited daily sign-ins.

Normal production sign-in volume has not been independently measured. The 20-message reserve is a planning floor, not a verified traffic estimate. Inspect actual Resend SMTP/API activity and daily reset before each wave, reserve more if needed and reduce/delay waves rather than purchasing an unnecessary upgrade. Do not automatically send welcome messages. Keep 30/hour as a proposal; do not change 2/hour under this implementation approval.

Prepared queue safeguards: configurable daily wave (15 default); serial claim/pacing; per-message idempotency; accepted vs delivered; signed callback dedupe; no retries after an unknown send; admin delivery visibility; same-day operator capacity check. The worker and callback gates remain off and no live scheduler/webhook is installed. A provider-capacity snapshot can age during a wave: recheck it before continuing; no automatic cross-provider quota reservation is claimed.

Before any real delivery: approve the exact recipients/cohort/wave and test email, review sender/template/token expiry and origin, approved worker ingress/schedule and rollback, verify recipient matching and signed webhook/manual monitoring. Monitor delivery, bounce/complaint, SMTP throttling, API 429s and unexpected participation. Stop on failure; inspect provider acceptance before resending. Never log personal invitation tokens or authentication links.
