# Focused local library security review

October 16, 2026. Implementation review and isolated tests, not an independent penetration test or professional food-safety review. Applies to PR #9's local application runtime; no hosted system was changed.

## Findings fixed during this pass

1. Ordinary title-only lookup could select a different signed revision/portion when the same title appeared in generated meals and Vault. Resolve the exact capsule/recipe and saved row identity; carry dessert metadata through the shared meal component.
2. Editable ingredient data could feed ordinary shopping/cache behavior. The local runtime bypasses those content caches, reconstructs records, and uses a server-aggregated basket. Unverified active-week content blocks the entire checked week, preventing a silently incomplete shopping list.
3. Shared root personalization could restore a different project's profile in a local engineering screen. Lab pages bypass that provider; the runtime has separate in-memory local auth and dedicated local clients. The application page also denies a mismatched ordinary public SDK URL/key. Use an isolated browser profile with no inherited real-account storage; the ordinary layout still imports its existing public SDK.
4. Global busy-fieldset disabling removed dialog return focus. Preserve the launching control and serialize actions with an in-flight lock instead.
5. Replacement results initially disappeared on inventory refresh; retain the new signed artifact in memory and reverify it. Same-request retries retain the original input/rejected payload, avoiding hash conflicts after rejection history changes.

## Verification and remaining release review

Automated tests cover tampering, malformed signatures, cross-owner capsules, original/current restrictions, changed avoidance, rotated/retired keys, edited persisted JSON, old unsigned content, transformed groceries, direct RLS/private-RPC denial, duplicate/concurrent reservations, expiry and account/plan preservation. The disposable service/browser exercise records real Auth → route → REST → PostgreSQL evidence separately.

Before a hosted pilot: independently review this code and its reviewed-revision activation boundary, freeze an exact qualified-review manifest, approve environment-isolated key management and UUID allowlist, validate deployment protection and data/retention scope, then repeat adversarial checks on the separately authorized protected environment. Do not simply remove the local-only guard or reuse a local key. No new database migration is currently required; any later schema change needs separate review and approval.
