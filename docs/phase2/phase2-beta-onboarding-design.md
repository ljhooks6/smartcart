# Beta onboarding, temporary access and feedback design

Design only: no migration, activation, invitations, grants or billing changes are implemented. The private starting targets stay configurable: 30 Free, 15 Plus and 5 Reserve. They are not public application promises. Existing accounts and guests remain usable independently of beta eligibility.

## Invitation sequence

Applied → Under Review → Approved/cohort assigned → invitation reserved → Invited → verified identity → explicit acceptance → Activated. Reserve remains a waiting cohort until an administrator promotes a candidate. Cohort counters distinguish approvals, reserved seats, valid outstanding invitations and activated testers. The acceptance transaction atomically checks configured capacity; resends do not reserve additional seats. Expired/revoked invitations release their reservation.

Use a new private beta_invitations table: applicant ID, program ID, immutable intended Auth user ID when known, normalized invited email, cohort, SHA-256 token hash, expiry, sent/accepted/revoked timestamps, accepted user ID, creator and version. Generate at least 256 random bits with the server cryptographic RNG; store only the hash. Proposed TTL seven days, resend cooldown 24 hours, maximum three resends/week, one valid invitation/applicant/program. All are private configuration and require approval. Rotation revokes older tokens atomically.

Use a fragment-based application invitation URL so the token is not sent in HTTP paths, referrers or ordinary access logs. On explicit user action, consume it via authenticated POST; strip it from navigation and keep it out of analytics, browser storage and error reports. Do not consume on GET or email scanner prefetch. Keep this separate from Supabase's existing authentication callback. After normal Google or magic-link login, require auth.getUser(), verified email matching the intended normalized recipient, and any previously bound UUID. Do not treat Gmail aliases/dot removal or a client email as authorization. A wrong logged-in account gets a clear switch-account path; its existing account/session is not globally revoked.

Prefer binding an existing verified Auth UUID before invitation, using a privileged lookup. Otherwise bind once at acceptance under a transaction/row lock. Never create duplicate users or use Supabase account invitations as beta grants. New users follow the existing signup/verification flow, then accept. Changed applicant email requires admin review and invitation revocation/reissue; it does not update auth.users. Same-email applicants cannot gain another person's account. Linking identities is not automatically enabled.

Activation transaction: lock invitation/applicant/capacity, verify current state and expiry using database time, compare identity, mark accepted once, bind applicant to user, create beta participation and (for Plus only) a separate grant, append audit record. Repeated acceptance by the same account can return the existing result; another account cannot reuse it. Declined/Withdrawn/revoked applicants cannot activate. Client status/cohort values are ignored. Revocation disables beta participation/grants only, preserving baseline product access, paid Plus and content.

Invite delivery needs a separately reviewed ledger/outbox. The Phase 1 ledger permits the single owner test key and is not an invitation ledger; do not silently broaden it. A worker claims a unique invitation version, issues its hash transactionally, and holds the raw token only in memory while submitting the email. Provider idempotency plus a durable unique send claim prevents duplicate sends. If outcome is uncertain, do not retry or regenerate automatically: reconcile provider metadata or have an administrator explicitly revoke/reissue. Never store the raw invitation URL in ledger/logs. A provider email necessarily contains the link; its retention/access must be disclosed. No automatic marketing or paid enrollment.

Audit events cover approval, cohort changes, invitation creation/send/revoke/accept, grant issuance/expiration/revocation and actor UUID. Browser roles have no invitation/grant writes. Applicant/user reads expose only safe own status; admin reads/writes require a server-verified UUID and private admin membership. Privileged SQL functions use explicit search_path and narrow grants. Retention deletes token hashes and applicant linkage according to the approved program policy after expiration/withdrawal; retain only minimal operational audit for the justified period. Document legal exceptions and export/deletion verification before migrations.

## Temporary Plus access

Separate beta_participations and beta_entitlements tables. An entitlement contains user UUID, program, Plus capability, starts_at, expires_at, revoked_at, source participation, granting actor and reason. No Stripe provider IDs; no update to smartcart_profiles.plan or smartcart_subscriptions. Enforce valid timestamp order and one current grant/user/program, with historical grants retained for audit.

Proposed default: 30 days from activation, capped at the configured program end; extensions/promotions are explicit audited admin actions. Effective Plus = legitimate existing server-authorized profile Plus **or** a current nonrevoked beta Plus grant. Preserve legacy legitimate profile Plus as well as paid subscribers; do not redefine Stripe status/grace rules. Free beta participation gives no premium override. Reserve gives no participation access until promoted. Paid Plus remains Plus when a beta grant expires, is revoked or changes to Free. A paid cancellation during a live beta grant leaves the separate complimentary grant valid until its own expiry; Stripe behavior is unchanged.

Database time governs expiry on every privileged operation, so enforcement does not depend on cron. Share one effective-entitlement definition across server membership, quota reservation, queued execution and database persistence functions. Do not trust a cached/client plan or token metadata. Initially avoid entitlement caching; show a server-derived beta badge/expiry separately from the paid subscription label. If a grant expires between queue reservation and processing, re-evaluate capabilities before generation and use the baseline Free behavior without duplicating quota consumption. Use tests to define this transition before implementation.

Plan inventory is in phase2-authentication-audit.md. Upgrade plan/model selection, cuisine and Plus quality at every relevant server route and worker. Add database enforcement to pantry writes and serialized vault inserts because current own-row RLS permits UI bypass. Preserve existing content read/export/delete rights. When Plus expires, keep all existing recipes/vault records; block new vault additions until below the Free cap of five. Freeze new Plus pantry-memory persistence, retain content, and allow privacy deletion. Do not delete pantry or excess vault meals on expiry. Ordinary meal planning, cooking and groceries remain available.

Required future tests: forged user/plan/cohort/admin input; cross-user RLS; direct pantry/vault writes; expired/not-started/revoked grant; paid Plus plus expired beta; cancellation plus active beta; concurrent promotion/revoke/accept; capacity race; resend invalidation; clock-boundary queued work; over-cap content preservation; DB outage fail closed. These are specified design acceptance tests, not yet implemented/executed.

## Lightweight tester feedback

Existing smart-cart-feedback.tsx supplies toasts/undo/confirmation, not a feedback submission service. A tester survey document exists but its 16-question format is too heavy for frequent mobile feedback. The existing Formspree general Plus waitlist stays unchanged and separate.

Add a small persistent Account/help entry for activated testers: category (bug, idea, confusing, Plus feedback), optional 1–5 experience rating, and a bounded 1000-character description. No attachments, device fingerprinting, health data, household budgets or extra email collection by default. Give a short reminder not to include sensitive data. Server derives user, participation/cohort and coarse app section; clients cannot assign a cohort or another tester identity. Use existing authentication/admin/rate-limit helpers and a new minimal RLS-protected table; do not require another paid survey service.

Tester can see own submissions; administrators can search/category-filter and set Open, Triaged, In Progress or Resolved, link duplicates and see outstanding counts. Plain text is escaped; no HTML execution. Rate-limit posts and bound payloads. Marketing consent is separate and never inferred from feedback. No automated email response. Proposed retention: 90 days after program end, with withdrawal/deletion handling and minimal anonymized trend counts only when lawful. This policy needs approval/legal review alongside existing applicant retention.

Invitation/receipt drafts must not promise feedback controls before this service exists. Accessibility acceptance: labelled fields, keyboard/screen-reader errors, status announcements, 44px targets, 320px layout and focus returned on close. No heavy modal survey.

## Security review disposition

Hash-only invitation storage, explicit POST acceptance, verified UUID/email binding, transactional capacity and immutable audit address the identified design threats. A schema alone does not prove security: perform the race/RLS/expiry tests before deployment. The server entitlement definition and pantry/vault database enforcement are required before complimentary Plus activation. No invitation/grant/feedback table is created in this stage.
