October 16, 2026. Continues the approved PR #9 milestone `49dc122` on `feature/allergy-aware-candidate`. **Draft and unmerged; no hosted deployment or activation.** This is a local engineering milestone, not approval of recipes or a public allergy feature.

## Delivered

- `/labs/allergy-aware/app` uses the ordinary `SmartCartApp` entry with an explicit local runtime and the existing Meals, Week, Cook, Shop, Vault, day-picker and interactive recipe components. The ordinary default runtime is unchanged. The local Plan form provides explicit four-source exclusions, avoidance, Vegetarian/Vegan preferences, equipment, pantry quantities, time, household size and budget. It calls no AI provider.
- Generated dinners and dessert can be selected individually, scheduled, read as fixed interactive recipes, saved to Vault, restored, replaced with compatible authored IDs, and marked cooked. Week and Shop follow selected recipes. The local cooked count lasts for that owner/session. Existing atomic jobs, quotas, access RPCs, authenticated storage/RLS and Vault caps are reused. There are no new migrations.
- Every checked recipe read/save/restore and basket transformation is server-verified. Original restrictions and avoidance survive new settings, replacement and storage. Signed identity, not title, distinguishes recipe artifacts. Unverified saved entries remain preserved; an affected active week is withheld and cannot be overwritten by the adapter.

Cooking checkoffs cannot authorize a recipe. Capsules are private readable metadata, not encrypted clinical records or safety certificates.
- Shopping aggregates full server-owned recipe requirements, including recipes from multiple signed plans. It does not deduct pantry quantities across plans or permit changed requirements, substitutions or household extras to inherit checked status. Collection checkmarks are presentation state. Store Mode's advanced workflow is not part of this candidate; the canonical sidebar, collection and rechecked copy path are available.
- [Focused security review](allergy-library-security-review.md), [ten-recipe calibration batch](allergy-review-packet/calibration-batch.md), exact hashes/specifications, [unsent outreach](allergy-review-packet/outreach-draft.md), and [all-48 cooking matrix](allergy-review-packet/physical-cooking-tests.md) are prepared. ## Isolation and local setup

Both lab flags, a development runtime, no Vercel markers, a loopback target/origin, explicit synthetic UUID allowlist and dedicated local Supabase/signing configuration remain mandatory. The successful application page additionally requires the ordinary public Supabase URL/anon key to match the dedicated disposable local service. This prevents accidentally running its ordinary layout against a shared project. Lab personalization skips shared profile loading. Use a **clean isolated browser profile**, not an existing real-user browser session.

Optional `MEALCADDIE_ALLERGY_LOCAL_KEY_RING` is a local JSON object with `active` key ID and at most five base64url 32-byte-or-longer `keys`. Keep retained verification keys explicitly; remove a compromised/retired key to withhold its old check states. Never copy local keys to hosting. No key values are committed. The existing single local key remains supported. No hosted credential, environment variable, account, beta record, subscription or shared database changed.

Reproduce using `scripts/test-allergy-library-local.mjs` with `RUN_DISPOSABLE_ALLERGY_LAB=1`, `MEALCADDIE_LOCAL_PG_MODULE` pointing to the installed local `pg`, `MEALCADDIE_TEST_LIBRARY_BROWSER=1`, and `MEALCADDIE_PLAYWRIGHT_MODULE` pointing to an installed Playwright. The existing unlinked loopback Auth lab and cached Docker images are prerequisites. The runner uses synthetic `example.invalid` accounts, a separately named throwaway database and REST container, a loopback proxy/server and ephemeral keys, then removes its own resources. It pulls no images and sends no email. Never supply production or Resend credentials.

## Minimum steps to a professionally reviewed protected pilot

1. **Owner approval to contact a named qualified reviewer**, using the unsent message/approved packet subset. Verify credentials/scope/conflicts; obtain and separately approve a capped quote, deliverables and material-use terms before engagement. No reviewer has been contacted or paid.
2. **Qualified review and physical cooking evidence** for the shared catalog/components, chosen recipe revisions, exclusion combinations, preparation/yields/time/scaling and UX claims. Start with the ten-recipe calibration batch; exclude unresolved candidates rather than reaching a target count. Review all claimed household sizes; do not assume tests at two servings validate twelve. Confirm realistic participant-facing privacy/retention and limitations.
3. Freeze the accepted revision/hash/scope manifest and implement its explicit hosted activation boundary after review. **Engineering-candidate availability locally must not itself authorize hosted use.** Perform independent security/release review, including environment-specific key/audience rotation, allowlist, stale-artifact handling and stop procedure.
4. **Separate approval** for the exact protected Preview code/configuration, environment-isolated credentials/test data and named pilot UUIDs. Keep Vercel Authentication and deny production/current beta participants. Repeat adversarial and end-to-end checks there; complete [NVDA, VoiceOver, TalkBack and physical-device gates](allergy-library-accessibility-checks.md).
5. Only then request **explicit participant notice/consent and pilot activation approval**, with reviewed recipes, bounds, monitoring and disable/rollback procedure. Disable the new mode/allowlist to stop the pilot and preserve stored content; do not lift the production allergy restriction or modify existing entitlements.

Open blockers are external qualification/cooking, revision-level hosted release gating/security approval, and full device/assistive-technology verification. Catalog-only prices/times remain engineering estimates. Arbitrary sauces/products, unsupported allergies, custom/unclear restrictions, intolerances and medical diets remain blocked. Cross-contact and brand formulations remain unverifiable. These are genuine pilot dependencies, not a request for another broad development cycle.
